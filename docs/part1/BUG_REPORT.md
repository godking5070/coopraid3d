# 개발 테스트 오류 보고 묶음

생성된 ZIP의 로컬 감시·분석 대기열 사용법은 [BUG_REPORT_WATCH.md](BUG_REPORT_WATCH.md)를 참조한다.

개발 빌드에서 별도 테스트 프로필을 지정해 실행한다: RaidPart1.exe --raid-test-profile=bugreport-01

오류 발생 → 가능하면 추가 조작 중단 → 왼쪽 위 **개발 테스트 · 오류 보고** → 필요한 재현 설명 입력(선택) → **오류 보고 묶음 내보내기** → 완료/부분 성공·누락 사유 확인 → **파일 위치 열기** → ZIP을 직접 전달한다. Unity 에디터 Play에서는 같은 프로필 인수로 에디터를 실행한 경우 Raid Rogue > 스킬 테스트 창에서도 수집 화면을 열 수 있다. 프로필 없이 실행한 개발 빌드와 일반 배포 빌드에는 수집 명령이 없다.

강제 종료 뒤에는 **같은 프로필 이름**으로 개발 빌드를 다시 실행하고, 새 게임·초기화 전에 묶음을 만든다. 재실행 전 메모리 상태는 알 수 없으며, ZIP은 새 실행의 메모리 요약, 현재/직전 테스트 세션 로그, 디스크의 체크포인트·정산·개인 진행 저장과 각 백업을 구분한다. 수집기는 강제 저장이나 복구를 실행하지 않는다. 첫 실행보다 앞선 로그를 소급 수집하지 않는다.

ZIP 위치: Windows %LOCALAPPDATA%\RaidRogue\BugReports\BugReport_YYYYMMDD_HHMMSS_ID.zip. 테스트 저장과 Steam Cloud 대상 폴더 밖이다. 테스트 원본 로그는 Unity 사용자 데이터의 test-profiles\<프로필>\diagnostics\session-*.log에 실행별로 남긴다. 저장 파일은 해당 프로필의 현재 계정 campaign\<계정>\에서 허용된 JSON 3종, .bak, 검증된 원자적 쓰기 임시 파일만 읽는다. 일반 저장, 다른 테스트 프로필, 설정, 인증 정보, Assets, Library, 스크린샷은 포함하지 않는다.

ZIP의 report.txt는 현재 메모리 상태와 마지막 확인 가능한 저장 상태를 따로 표시한다. manifest.tsv는 수집한 사본의 크기·SHA-256과 빠진 파일의 사유를 기록한다. collection-status.txt는 전체/부분 성공과 경고를 보여 준다. 로그는 파일당 최근 4 MiB를 보존하고 앞부분 생략량을 적는다. 테스트 로그는 실행 중 8 MiB마다 새 파일로 이어 기록하며 기존 로그를 삭제하지 않는다. 현재 묶음에는 최신 실행 파일과 직전 실행의 최신 파일이 들어간다. 원본 저장·로그·백업은 수정하지 않는다.

수집 사본에서 Steam ID, 긴 계정 번호, Windows 경로, 이메일, IP, JSON 플레이어 이름과 알려진 자격 증명 패턴을 익명화한다. 저장 JSON에 자격 증명으로 의심되는 필드가 있으면 파일 전체를 ZIP에서 제외하고 사유를 표시한다. 자유 형식 텍스트에 들어간 모든 개인정보를 완벽하게 판별할 수는 없으므로, 외부 전달 전에 ZIP을 직접 확인한다.

Unity 네이티브 프로세스가 로그 콜백 전에 중단되거나 크래시 덤프만 남기면 테스트 세션 로그에는 원인이 없을 수 있다. 공유 Player.log와 Unity 크래시 덤프는 다른 프로필/계정 자료가 섞일 수 있어 자동으로 ZIP에 넣지 않는다. 이 경우 Unity 버그 리포트와 ZIP을 별도로 확인해 전달한다.

확인 순서: 테스트 프로필로 실행 → 오류 한 건 발생 → 설명 없이 한 번 내보내기 → ZIP 열기/목록과 manifest 비교 → 앱 재시작 → 같은 프로필에서 직전 로그가 분리되어 들어가는지 확인 → 기존 저장의 수정 시각·해시 비교. 일반 저장은 건드리지 않는다. 실제 강제 종료·재시작, 실행 중 저장과 동시 수집, Unity 개발/일반 배포 빌드의 UI 확인은 원본 Unity에서 별도 Play 확인이 필요하다.
